# Feature Specification: Minimal Interview UI

**Feature Branch**: `[002-minimal-interview-ui]`  
**Created**: 2026-03-15  
**Status**: Draft  
**Input**: User description: "Minimal UI for the AI interview Engine. This UI should do only three things: Start an Interview session, display questions, submit answers and show evaluation results. Nothing else. The backend already handles the real logic. I want it to look sleek and modern."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Start An Interview (Priority: P1)

As a candidate or interviewer, I want to start an interview session from a single, focused screen so I can move immediately into the interview without setup friction or unrelated controls.

**Why this priority**: Without session start, the UI provides no value. This is the entry point that unlocks every other task.

**Independent Test**: Can be fully tested by opening the UI, entering the required interview setup inputs, starting a session, and verifying that the first question appears with no dependency on later answer submission flows.

**Acceptance Scenarios**:

1. **Given** the user is on the initial screen, **When** they provide valid interview setup details and start the interview, **Then** the system creates a session and displays the first question.
2. **Given** the system cannot start a session, **When** the user submits the start action, **Then** the UI shows a clear error state and keeps the user on the start screen with their inputs preserved.
3. **Given** a session is being created, **When** the user initiates the start action, **Then** the UI shows a clear loading state and prevents duplicate session creation actions until the request completes.

---

### User Story 2 - Answer Questions And See Results (Priority: P2)

As a candidate or interviewer, I want to read each question, submit an answer, and see the evaluation outcome in context so I can understand performance question by question.

**Why this priority**: This is the core workflow after session start. The product is only useful if it lets users complete the interview loop and see the evaluation feedback generated by the backend.

**Independent Test**: Can be fully tested by starting or loading a session, entering an answer for one question, submitting it, observing the pending state, and confirming that the evaluation result appears for that answer.

**Acceptance Scenarios**:

1. **Given** a session with available questions, **When** the user selects or lands on a question, **Then** the UI displays the question content and its position within the interview.
2. **Given** the user has entered an answer, **When** they submit it, **Then** the UI shows that the answer was accepted and that evaluation is in progress until a result is available.
3. **Given** an evaluation result is available, **When** the UI refreshes that answer state, **Then** the user can see the score and feedback associated with that submitted answer.
4. **Given** answer submission fails, **When** the request returns an error, **Then** the UI preserves the typed answer and presents a retry path without losing context.

---

### User Story 3 - Stay Focused In A Modern Interface (Priority: P3)

As a user, I want the interview UI to feel sleek, modern, and intentionally minimal so I can stay focused on the interview rather than navigating clutter.

**Why this priority**: The user explicitly wants a modern visual experience, but this comes after the core interview flow. It improves usability and perception without changing backend behavior.

**Independent Test**: Can be fully tested by reviewing the interface on common desktop and mobile-sized screens and verifying that the start flow, question view, answer input, and evaluation display remain visually clear and focused.

**Acceptance Scenarios**:

1. **Given** the user is using the UI on a common desktop or mobile screen size, **When** they move through the interview flow, **Then** all primary actions remain visible and usable without unrelated panels or controls.
2. **Given** the user is viewing different states of the interview flow, **When** the UI transitions between start, question, pending, and result states, **Then** the layout remains visually consistent and easy to scan.

---

### Edge Cases

- What happens when the backend returns zero questions or an incomplete question set for a newly started session?
- How does the UI behave when evaluation remains pending longer than expected for a submitted answer?
- What happens when the user navigates between questions where some answers are unanswered, some are pending evaluation, and some are already completed?
- How does the UI handle a page refresh or revisit while an interview session is still active?
- What happens when a submit action succeeds but the evaluation result is temporarily unavailable or delayed?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST provide a single interview start screen where the user can enter the minimum required setup information to create an interview session.
- **FR-002**: The system MUST create an interview session through the existing backend and move the user into the question flow after a successful start.
- **FR-003**: The system MUST display one question at a time with enough context for the user to understand which question they are answering and where they are in the interview.
- **FR-004**: The system MUST provide a text input area for answering the currently displayed question.
- **FR-005**: The system MUST allow the user to submit an answer for the current question and MUST clearly acknowledge that the submission was accepted.
- **FR-006**: The system MUST show the current answer state for each submitted response, including pending evaluation, completed evaluation, and failed evaluation states when provided by the backend.
- **FR-007**: The system MUST display evaluation details returned by the backend for a completed answer, including the overall score and narrative feedback.
- **FR-008**: The system MUST allow the user to move between questions within the active session and MUST clearly indicate which questions are unanswered, awaiting evaluation, or completed.
- **FR-009**: The system MUST preserve the user’s typed answer content if an answer submission attempt fails so the user can retry without retyping.
- **FR-010**: The system MUST present clear loading, empty, and error states for session creation, question retrieval, answer submission, and evaluation retrieval.
- **FR-011**: The system MUST keep the UI scope limited to starting an interview, viewing questions, submitting answers, and viewing evaluation results.
- **FR-012**: The system MUST avoid exposing backend-only concepts, operational controls, or administrative workflows that are not required for the three core user tasks.
- **FR-013**: The system MUST provide a visually polished and modern presentation that remains readable and usable on both desktop and mobile-sized screens.

### Key Entities *(include if feature involves data)*

- **Interview Session**: A single interview run initiated from the UI, including setup details, overall session status, and its ordered set of questions.
- **Interview Question**: A prompt within a session, including its content, order, and current answer/evaluation state as presented to the user.
- **Candidate Answer**: A user-submitted response tied to a specific question, including its content and submission status.
- **Evaluation Result**: The backend-generated assessment for a submitted answer, including score, written feedback, and result status.

### Assumptions

- The UI uses the backend’s existing interview and evaluation capabilities without introducing new scoring logic or manual review workflows.
- A single active interview session per user/browser context is sufficient for this minimal UI.
- Evaluation results may arrive asynchronously after answer submission, so the UI should communicate waiting states without blocking the rest of the session.

### Out Of Scope

- User accounts, sign-in flows, and saved interview history.
- Administrative dashboards, analytics screens, rubric editing, or prompt configuration.
- Candidate profile management, interviewer collaboration features, or export/reporting flows.
- Additional interview features beyond the three requested tasks.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: In usability testing, at least 90% of first-time users can start an interview and reach the first question in under 30 seconds without assistance.
- **SC-002**: At least 95% of successful answer submissions show a visible acknowledgement or pending state within 2 seconds of the user action.
- **SC-003**: When an evaluation result becomes available, it is shown to the user without a page reload in at least 95% of observed test runs.
- **SC-004**: On both mobile-sized and desktop-sized screens, 100% of the three core tasks can be completed without horizontal scrolling or hidden primary actions.
- **SC-005**: In stakeholder review, at least 4 out of 5 reviewers agree that the UI feels modern, focused, and free of non-essential screens or controls outside the three defined tasks.
